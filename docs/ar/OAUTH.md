# تسجيل الدخول إلى موصّلات MCP البعيدة (OAuth)

[English](../OAUTH.md) · **العربية**

بعض الموصّلات لم تعد تطلب منك نسخ رمز. تضغط **تسجيل الدخول** وتوافق على الوصول في متصفحك، فيحفظ VARA النتيجة في خزنته المشفّرة. تقول هذه الصفحة ما يفعله VARA، و**ما عليك فعله بنفسك**، وبصراحة: ما الذي **لم يُجرَّب** على الخدمات الحقيقية.

> **الحالة: مُنفَّذ ومُختبَر على خادم وهمي فقط.** المسار كاملاً (الاكتشاف، التسجيل الديناميكي، PKCE، التجديد، الإلغاء، بديل اللصق، فحوص العناوين) يعمل في `tests/oauth.test.ts` ضد خادم تفويض وهمي محلي. **لم يُشغَّل على GitHub ولا Notion ولا Sentry ولا Supabase.** توقّع مفاجأة أو اثنتين في أول اتصال حقيقي؛ قسم [إذا لم يعمل](#إذا-لم-يعمل) يذكر أرجحها.

## الموصّلات

| معرّف الموصّل | الخدمة | الخادم | التسجيل |
| --- | --- | --- | --- |
| `notion-remote` | Notion | `https://mcp.notion.com/mcp` | تلقائي (متوقَّع) |
| `sentry-remote` | Sentry | `https://mcp.sentry.dev/mcp` | تلقائي (متوقَّع) |
| `supabase-remote` | Supabase | `https://mcp.supabase.com/mcp` | تلقائي (متوقَّع) |
| `github-remote` | GitHub | `https://api.githubcopilot.com/mcp/` | **تنشئ تطبيق OAuth مرة واحدة** (أدناه) |

العناوين مأخوذة من توثيق MCP لكل خدمة؛ و«متوقَّع» تعني أن الخدمة توثّق التسجيل الديناميكي للعملاء، لا أن VARA رآه يعمل. موصّلات الرمز القديمة (`github` و`notion` و`sentry` و`supabase`) لم تتغير وتعمل برمز تلصقه — وهي البديل إن تعذّر تسجيل الدخول.

## تسجيل الدخول

**في واجهة المتصفح** (الإعدادات ← الموصّلات): اضغط **تسجيل الدخول** بجانب الموصّل، ثم **افتح صفحة تسجيل الدخول**، وافق على الوصول فتُغلق النافذة وحدها. يُضاف الموصّل ويتصل.

**في الطرفية:**

```bash
vara connectors login notion-remote
```

يطبع VARA العنوان ويحاول فتحه. وافق على الوصول؛ وحين تقول الصفحة إنك سجّلت الدخول ينتهي VARA.

**تسجيل الخروج** (الإعدادات ← الموصّلات ← تسجيل الخروج، أو `vara connectors logout <id>`): يطلب VARA من الخدمة إلغاء الرمز إن كانت تتيح ذلك، ثم يحذف كل ما خزّنه. وحذف الموصّل يفعل الشيء نفسه. وإن لم تكن للخدمة نقطة إلغاء يقول VARA ذلك — فاحذف VARA أيضاً من إعدادات الخدمة نفسها («التطبيقات المصرَّح لها»).

### حين يكون المتصفح على حاسوب آخر (خادم VPS)

تنتهي الموافقة بأن تحوّل الخدمةُ متصفحك إلى `http://127.0.0.1:<المنفذ>/callback?code=…`. إن كان VARA على خادم ومتصفحك على لابتوبك فهذا العنوان يشير إلى لابتوبك، فلن تُحمَّل الصفحة. **هذا متوقَّع.** افعل ما يلي:

1. على الخادم: `vara connectors login notion-remote --no-open` (أو اضغط تسجيل الدخول في الواجهة).
2. افتح العنوان المطبوع على لابتوبك ووافق.
3. يعرض المتصفح صفحة خطأ. **انسخ العنوان كاملاً من شريط العنوان** (يبدأ بـ `http://127.0.0.1:…/callback?code=…&state=…`).
4. الصقه في سطر الطرفية، أو في خانة **المتصفح على حاسوب آخر؟** في نافذة الويب، ثم **إنهاء تسجيل الدخول**.

يحوي العنوان رمزاً يُستعمل مرة واحدة ولهذا التسجيل وحده؛ ويتحقق VARA من `state` داخله ويرفض غيره. بديل: وجّه المنفذ ليصل التحويل إلى الخادم وحده — `vara connectors login <id> --port 8765` على الخادم و`ssh -L 8765:127.0.0.1:8765 you@server` على لابتوبك، ثم وافق كالمعتاد.

## ما عليك فعله أنت

### Notion وSentry وSupabase (يُتوقَّع تسجيل تلقائي)

1. شغّل `vara connectors login <id>` (أو اضغط تسجيل الدخول).
2. في الصفحة التي تُفتح **سجّل الدخول إلى الخدمة** واختر مساحة العمل / المؤسسة / المشروع الذي تسأل عنه. اقرأ الصلاحيات المعروضة — هذا هو الوصول الذي سيحصل عليه الوكيل.
3. انتهى. لا شيء تسجّله ولا تلصقه.

إن ردّ VARA بـ*«this server does not offer automatic app registration»* (أو رُفض التسجيل) فالخدمة تريد منك إنشاء تطبيق:

1. في لوحة الخدمة أنشئ **تطبيق OAuth / تكاملاً** (Notion: *Settings ← Connections ← Develop or manage integrations* وتكامل **عام**؛ Sentry: *Settings ← Developer Settings ← Custom Integrations / OAuth*؛ Supabase: *Organization ← OAuth Apps*). أسماء هذه الشاشات تتغير؛ ابحث عن «OAuth».
2. **عنوان التحويل / الـcallback:** `http://127.0.0.1:8765/callback` (وسجّل الدخول دائماً بـ`--port 8765` لأن العنوان يجب أن يطابق تماماً).
3. انسخ **client id** (و**client secret** إن عرضته الخدمة) واحفظهما — تُسأل عن القيم دون إظهارها:

```bash
vara secret set OAUTH_CLIENT_ID_NOTION_REMOTE
vara secret set OAUTH_CLIENT_SECRET_NOTION_REMOTE      # فقط إن أعطتك الخدمة سراً
vara connectors login notion-remote --port 8765
```

الأسماء دائماً `OAUTH_CLIENT_ID_<ID>` و`OAUTH_CLIENT_SECRET_<ID>` ومعرّف الموصّل بأحرف كبيرة وتُحوَّل `-` إلى `_` (`sentry-remote` ← `OAUTH_CLIENT_ID_SENTRY_REMOTE`). بلا السر يدخل VARA كعميل عام مع PKCE.

### GitHub (تنشئ تطبيق OAuth أولاً)

لا يُتوقَّع أن يسجّل خادم GitHub البعيد التطبيقات تلقائياً، فمرة واحدة على github.com:

1. **Settings ← Developer settings ← OAuth Apps ← New OAuth App.**
2. *Application name:* `VARA`. *Homepage URL:* أي عنوان تملكه، مثل `https://github.com/VARA-TEAM/vara-cli`.
3. **Authorization callback URL:** `http://127.0.0.1:8765/callback`
4. سجّل التطبيق ثم **Generate a new client secret**. انسخه فوراً — يعرضه GitHub مرة واحدة.
5. احفظ الاثنين:

```bash
vara secret set OAUTH_CLIENT_ID_GITHUB_REMOTE
vara secret set OAUTH_CLIENT_SECRET_GITHUB_REMOTE
```

6. سجّل الدخول بالمنفذ الثابت: `vara connectors login github-remote --port 8765`. (يقول توثيق GitHub إن عنوان loopback يمكن أن يستعمل أي منفذ، فقد ينجح المنفذ العشوائي أيضاً؛ والثابت هو الخيار الآمن. في واجهة الويب المنفذ عشوائي — فاستعمل أمر الطرفية لـGitHub أول مرة.)
7. **النطاقات (scopes):** لا تُدخلها عند إنشاء التطبيق. يطلب VARA `repo read:user` عند تسجيل الدخول وتعرضها صفحة موافقة GitHub. و`repo` تشمل الكتابة على المستودعات الخاصة — إن كان هذا أكثر مما تريد فاستعمل موصّل `github` مع **رمز وصول شخصي دقيق (fine-grained)** تحدد فيه المستودعات والصلاحيات بدقة، وهو الخيار الأضيق.

هل يقبل خادم GitHub البعيد رمز تطبيق OAuth التقليدي؟ **لم يُتحقَّق هنا.** إن اكتمل تسجيل الدخول لكن الموصّل أظهر خطأ تفويض فهذا هو السبب المرجَّح: استعمل موصّل الرمز.

## ما يفعله VARA وما يحتفظ به

- **الاكتشاف:** يسأل خادم MCP عن بيانات المورد المحميّ (تلميح `WWW-Authenticate` ثم العناوين المعروفة)، ثم بيانات خادم التفويض، ويتأكد أن الخادم يسمّي نفسه الجهة التي وُصل إليها.
- **التسجيل:** بـ`OAUTH_CLIENT_ID_<ID>` من الخزنة إن وضعته؛ وإلا بالتسجيل الديناميكي (RFC 7591) إن عرضه الخادم؛ وإلا يتوقف مع التعليمات أعلاه.
- **التبادل:** رمز التفويض + PKCE (S256) ومعامل `resource` و`state` عشوائي يجب أن يعود كما هو، والتحقق من الجهة المصدِرة (`iss`) إن أُرسلت. مستمع محلي على `127.0.0.1` (منفذ عشوائي أو `--port`) يلتقط التحويل ثم يغلق نفسه؛ يُستعمل الرمز مرة واحدة؛ وتنتهي المحاولة بعد 5 دقائق.
- **الرموز:** رموز الوصول والتجديد وأي client secret تُخزَّن **في الخزنة المشفّرة فقط** (سر واحد اسمه `OAUTH_TOKENS_<ID>`) وتُسجَّل في أداة الحجب، فلا تظهر في المحادثات ولا السجلات ولا مخرجات الأدوات. لا تعيدها أي واجهة برمجية ولا تُعرض في واجهة المتصفح ولا تُعطى للوكيل. قائمة الموصّلات تُظهر فقط *مسجَّل الدخول أم لا* وإمكان التجديد وموعد انتهاء رمز الوصول.
- **التجديد:** الرمز الذي يوشك على الانتهاء (خلال دقيقة) يُجدَّد قبل الطلب، وتجديد واحد تشترك فيه الطلبات المتزامنة؛ وخطأ `401` يسبب تجديداً واحداً وإعادة محاولة واحدة. ورمز تجديد مُلغى ينتهي برسالة واضحة «سجّل الدخول من جديد».
- **للمالك فقط:** بدء تسجيل الدخول وإنهاؤه وإنهاء الجلسة كلها واجهات للمالك (`/api/manage/connectors/:id/login|logout`)؛ لا يصل إليها الضيوف ولا الوكيل. وأداة `connector_manage` للوكيل ترفض إضافة موصّل تسجيل دخول لم يُسجَّل دخوله.
- **العناوين:** كل عنوان يتصل به VARA هنا — الخادم وبياناته والنقاط التي تذكرها البيانات وكل تحويل — يجب أن يكون `https` (و`http` العادي فقط على loopback، وفقط حين يكون خادم MCP نفسه على loopback أي خادم اختبار محلي). تُرفض عناوين الشبكات الخاصة وlink-local وCGNAT وبيانات السحابة (metadata) والعناوين التي تحمل اسم مستخدم، بنفس قواعد سياسة الأصول في أداة المتصفح. **حدّ:** الفحص على العنوان كما كُتب؛ والاسم العام الذي يُحَلّ سراً إلى عنوان خاص لا يُكتشف (لا تثبيت DNS).

## إذا لم يعمل

| ما تراه | السبب المرجَّح | ما تفعله |
| --- | --- | --- |
| *does not offer automatic app registration* | الخدمة تريد تطبيقاً مسجَّلاً | خطوات «أنشئ تطبيقاً» أعلاه |
| *the server refused to register VARA* | رُفض التسجيل الديناميكي أو قُيِّد | الشيء نفسه |
| *redirect_uri mismatch* في صفحة الخدمة | عنوان التحويل في التطبيق مختلف | استعمل `--port 8765` والعنوان `http://127.0.0.1:8765/callback` تماماً |
| الصفحة بعد الموافقة لا تُحمَّل | المتصفح على حاسوب آخر | الصق العنوان، [أعلاه](#حين-يكون-المتصفح-على-حاسوب-آخر-خادم-vps) |
| *the sign-in was not completed within 5 minutes* | تأخرت | ابدأ من جديد |
| سُجّل الدخول لكن الموصّل يقول 401 / forbidden | الخدمة تريد نطاقات أخرى أو نوع تطبيق آخر | راجع توثيق MCP للخدمة؛ وارجع إلى موصّل الرمز |
| *sign in again* بعد مدة | رمز التجديد أُلغي أو انتهى | `vara connectors login <id>` |

## لم يُنجز

- لا تدفق device-code (التحويل إلى loopback مع بديل اللصق يغطي الخادم بلا واجهة).
- لا إعادة تفويض تلقائية لنطاقات إضافية بعد `403`.
- لا تسجيل دخول لخوادم stdio (npx) — تأخذ رموزها من الخزنة كما كانت.
- Linear وSlack وGoogle وغيرها من خدمات OAuth ليست في الفهرس؛ لا يُضاف موصّل إلا بعد قراءة عنوانه في توثيقه. تسجيل الدخول يعمل لموصّلات الفهرس فقط؛ خادم MCP مخصَّص لا يستطيع بدء OAuth بعد.
- موصّلات تسجيل الدخول الأربعة أعلاه **لم يُسجَّل الدخول بها على الخدمات الحقيقية** في هذا الإصدار.
